# MySQL Schema (Backend, CMD-019)

The backend database is `urbantransit_iq` (MySQL 8.0, inside WSL). The schema is managed with
**Flask-Migrate** (Alembic), which works like Laravel migrations or TypeORM migrations:

```bash
flask db upgrade                     # apply database/migrations/versions/* (php artisan migrate)
flask db migrate -m "message"        # generate a migration after editing src/models (make:migration, autogenerated)
```

Migration `a7e1187bcc81_initial_backend_schema` creates 43 tables (plus `alembic_version`).

## 2. Phase 5 analytics mirrors (30 of 41 tables)

Each table mirrors `hdfs:///urbantransit/analytics/<name>`. The column list is copied from the
Parquet schema into `src/models/analytics.py` (`ANALYTICS_SCHEMAS`): **same names, same order,
same types, all nullable**. The mixed decimal precisions are kept, e.g. `decimal(6,4)` for most
shares, `decimal(16,1)` for `underutilization_score`, `decimal(30,3)` for
`active_days_per_week` and `decimal(14,2)` for `active_span_weeks`. Each table also gets a
surrogate `id` primary key (Parquet rows have no key), which the API never returns.

| Spark type | MySQL type |
|---|---|
| `string` | `VARCHAR(64)`. Exceptions sized from measured maximum lengths: `route_performance.class_reason` TEXT (322 chars), `tricky_case_notes`, `special_event_dates.spiking_routes`, `anomalies.detail` VARCHAR(255) |
| `int` / `bigint` | `INT` / `BIGINT` |
| `double` | `DOUBLE` |
| `decimal(p,s)` | `DECIMAL(p,s)` |
| `date` | `DATE` |
| `boolean` | `TINYINT(1)` |

Indexes are on the API filter columns: `route_id`, `stop_id`, `origin_stop_id`,
`destination_stop_id`, `direction`, `day_class`, `time_period` and `service_date`.

## 3. Reference tables (admin CRUD)

`routes` (118), `stops` (756) and `vehicles` (775) are loaded from the Phase 3 clean
Parquet. Their columns and NOT NULL rules follow `documentation/schemas/<table>.json`.
`dq_flags` is stored as JSON and `_source_file` is not copied. Admin edits change only the
MySQL copy. The analytics pipeline keeps reading HDFS, so analytics show the data as it was
when Phase 5 ran. The loader overwrites these tables only with `--force-reference`.

## 4. Model evidence

### `model_metrics` (340 rows from 28 files)

The Phase 6 JSON files (`models/spark/metrics/*.json`) use several layouts. The loader
flattens them into one row per number:

| column | meaning |
|---|---|
| `source_file` | metric file name; several files share an `algorithm` (e.g. four `random_forest` variants) |
| `task`, `algorithm` | as written in the file |
| `split_type` | `train`, `validation`, `test` (main and full-data runs); `validation_sample`, `test_full` (10% sample runs); `validation_tuning`, `validation_selection`; `validation_trial` (one per hyperparameter trial); clustering uses `train` (fitted on train-period route profiles) |
| `metric_name` | as written: `accuracy`, `macro_f1`, `weighted_f1`, `per_class_f1[<label>]`, `mae`, `rmse`, `r2`, `mape`, `silhouette`, `actual_clusters` (degenerate bisecting k-means) |
| `metric_value` | the number |
| `extra_json` | everything that is not a single number: `rows`, `k`, `split_dates`, `features`, `numeric_features`, `model_scope`, `training_fraction`, `selected_params`, `class_weights`, `confusion_matrix_long`, trial `params`, `status`, `date`, ... |
| `validity_flag`, `validity_note` | `INVALID` for every `delay_severity` row; NULL otherwise |

Layouts handled: main Spark runs, 10% sample runs, full-data weighted retrains (per-class F1
and confusion matrix), XGBoost (`test` + `validation_selection`), the demand baseline, and
clustering (`silhouette`, or `status` + `actual_clusters`). Rows per task: delay_severity 169,
daily_boardings 88, crowding_flag 74, route_clustering 9.

> **delay_severity metrics are INVALID.** Every delay-severity model, including the
> 2026-09-26 full-data retrains, lists `occupancy_pct` as an input feature
> (`spark_jobs/phase6_retrain_ab_wsl.py`; `numeric_features` in the enhanced JSON files).
> `occupancy_pct` is a *same-trip outcome* (`documentation/feature_catalog.md`), known only
> after the trip. Those scores overstate what a model could do before departure. They are
> shown for transparency and **must not be used to serve predictions** until the model is
> retrained without that feature.

**Open question (not flagged):** the enhanced crowding and delay feature lists also contain
`travel_time_min` and `headway_minutes`. The feature catalog also classes both as same-trip
outcomes. This needs a decision before any crowding model is served.

### `cluster_profiles` (4 rows)

Loaded unchanged from `reports/phase6_cluster_profiles.csv`: `prediction` (cluster id), the
eight mean route features, `routes` and `plain_language_label`. **No route-to-cluster
assignment exists yet**, so there is no table mapping routes to clusters.
