# Dataset Generation Methodology

UrbanTransit IQ uses its own synthetic public-transport dataset, generated by the code
in `data_generator/`. No ready-made dataset is downloaded. This document explains *how*
the data is produced; the *measured results* (volumes, patterns, defect counts) are in
[dataset_statistics.md](dataset_statistics.md), computed from the generated files.

## 1. Design principle: simulate first, derive second

The generator does not fill each table with independent random rows. It runs one
simulation of a bus network and then *projects* that simulation into the tables:

```
network (stops, routes, route_stops, fleet) + calendars + schedules + passengers
        |
        v
 month by month: plan trips from timetables -> simulate each trip
   (vehicle, departure deviation, passengers waiting, load, running time)
        |
        +--> trips             scheduled vs actual departure/arrival, vehicle, status
        +--> passenger_counts  APC boardings / alightings / peak load for that trip
        +--> tickets           one row per smart-card tap on that trip (tap-in/tap-out)
        +--> delays            stop-level scheduled vs actual times + reason
        +--> gps_events        positions interpolated from the same stop times
```

Because every derived table comes from the same simulated trip, they agree:
ticket tap-in/out times sit between the trip's actual stop times, `card_taps` in
`passenger_counts` equals the number of ticket rows for the trip, a delay record's
`delay_minutes` equals `actual_arrival - scheduled_arrival` to the second, and GPS
pings lie on the route between the stops the trip served. Realistic noise is added
where real systems have it (APC alighting counts, GPS position noise, tap-in within
the dwell time).

## 2. Tables and formats

12 tables, defined in `documentation/schemas/*.json` (columns, types, PK, FK) - see
[data_dictionary.md](data_dictionary.md) and [erd.md](erd.md).

| Table | Format | Files |
|---|---|---|
| stops, routes, route_stops, vehicles, passengers, schedules | CSV | one file each |
| service_calendar | JSON (array with nested `exceptions`) | one file |
| trips, passenger_counts, tickets, delays | CSV | **one file per month** (`<table>_YYYY-MM.csv`) |
| gps_events | JSON Lines | **one file per day** of the GPS window |

Splitting the large tables by month makes multi-file ingestion meaningful in Phase 2
(e.g. 12 monthly ticket files read as one DataFrame).

**Why tickets are a subset of boardings.** `passengers` are *registered smart-card
holders*. Cash riders are counted by the automatic passenger counters (APC) but leave no
ticket record. The card share of boardings is a config parameter that grows through the
year (smart-card adoption); it was tuned so the ticket volume clears the SRS minimum with
a safety margin while bus loads stay realistic.

**Why `passenger_counts` has fewer rows than `trips`.** Only APC-equipped vehicles
(`vehicles.has_apc`) produce counts, and cancelled trips produce none.

**GPS sample size.** A real AVL feed pings every 10-30 s; for ~2 million trips a year that
would be hundreds of millions of rows (tens of GB), which adds nothing to the analytics
this project needs and would not fit comfortably on the 8 GB WSL budget. The generator
therefore simulates a **7-day window** (Mon-Sun, including a special event) for **all
trips** in that week, with one ping at each stop (departure/arrival) and one mid-segment
"in transit" ping. That is enough for bunching/headway, speed and map analyses and stays
a few hundred MB.

## 3. The simulation

### 3.1 Network
* 28 real Lahore landmarks are hubs. Routes are polylines between points chosen by route
  type (BRT crosses the city through the centre, trunk routes run from the edge to a central
  hub, local routes link neighbourhoods to hubs, feeders run from the edge to the nearest hub).
* Stop points every 0.55-1.0 km along a route. A point within 350 m of an existing stop
  reuses that stop, so routes share stops at hubs and corridors.
* The most shared stops (6%) are **bottleneck junctions** (hidden from the output).
* Fleet: per route, `ceil(round-trip time / tightest peak headway) + 1` vehicles of the
  route's type (articulated 150, standard 70, minibus 30 total capacity), plus depot spares.

### 3.2 Calendars and schedules
* Timetable periods autumn 2025, winter/spring 2026, summer 2026 (and autumn 2026 for
  `hidden_like`), each with weekday / Saturday / Sunday service calendars, a Ramadan weekday
  calendar and a holiday calendar (holidays are GTFS-style exceptions).
* Schedules give a headway and planned running time per route, direction, service and
  time period (early, AM peak, midday, PM peak, evening). New periods change headways
  (e.g. more frequent peak service from January, reduced off-peak service in summer).

### 3.3 Demand (who is waiting for the bus)
Passengers arriving per minute for a trip =
`route base rate x hourly profile x peak-direction boost x month factor x day-of-week factor x holiday/Eid factor x weather x event multiplier x new-route ramp-up x daily noise`.
The number waiting when a bus arrives is that rate times the **actual** gap since the
previous bus, with over-dispersion (gamma-Poisson).

### 3.4 Operations model (sequential, per route and day)
For each trip in time order:
1. take the earliest-available vehicle of the route's pool; if it is still finishing its
   previous trip, this trip starts late (**delay propagation**);
2. compute the gap since the previous departure in the same direction -> passengers
   waiting -> boardings; a bus above 1.3x capacity leaves people behind (**denied boardings**);
3. running time = planned + traffic + junction bottlenecks + weather + events + road works
   + disruptions + breakdown + **boarding-driven time**, where boarding-driven time =
   `dwell_per_boarding_min x (boardings - normal boardings)`
   + `bunching_sensitivity x planned time x (actual gap / scheduled headway - 1)`
   + a crowding penalty above 85% occupancy. Light buses can run early (limited to 18% of
   planned time);
4. breakdowns swap in a depot spare (**vehicle change**, `original_vehicle_id`); the load is
   capped at the spare's own crush capacity and the broken bus leaves the route for the day.

The bunching term is the classic headway-instability mechanism: a bus that departs after a
longer gap meets more waiting passengers at every stop and keeps losing time, while the
bus behind it finds empty stops and catches up. Departures from the terminal stay close to
the timetable, but irregular headways and **bunching appear downstream** (measured at the
last stop in [dataset_statistics.md](dataset_statistics.md)). The knobs live under
`operations:` in `generator_config.yaml` and were tuned with `data_generator/tune_check.py`
(in-memory dry runs, see COMMAND_LOG CMD-008).

## 4. How each realism feature is produced

| Feature | Mechanism (code) |
|---|---|
| Peak hours | Hourly profiles `P_WK_IN/OUT` (weekday), `P_SAT`, `P_SUN`, `P_RAM_IN/OUT` in `simulation.py`; peak headways in `calendar_schedules.py` |
| Weekday vs weekend | Day-of-week factors + separate weekend profiles and weekend timetables |
| Seasonal demand | `MONTH_FACTOR` (summer holidays, monsoon, winter) |
| Holidays | Holiday service calendar (exceptions) + holiday/Eid demand factors |
| Direction differences | Inbound (towards the centre) peaks in the morning, outbound in the evening, plus `peak_direction_boost` |
| Low-demand and overcrowded services | Lognormal route base rates by type; crush-load cap with denied boardings |
| Delays vs load | Dwell time grows with boardings above normal; crowding penalty above 85% of capacity; crush load 1.3x capacity |
| Delays vs time of day | Running-time ratio per period (`CONG_MU_*`), junction penalty larger in peaks, fog mornings |
| Delays vs stops | Bottleneck junctions weigh 6x in how delay accumulates along the route; delay records are logged at the stop with the largest delay increase |
| Irregular headways, bunching | Headway-instability feedback + delay propagation + departure deviation (section 3.4) |
| Cancellations | Base rate + fog mornings, driver-shortage days, protests; reason recorded |
| Early arrivals | Light off-peak trips run early; logged as `early_running` |
| Vehicle changes | Breakdowns swap in a spare (`original_vehicle_id`) |
| Special events and spikes | Configured events: demand multiplier on routes within 1 km of the venue, extra `event_extra` trips, local delays |
| New routes / stops / schedules | 8 routes launched mid-period (with new stops and a 60-day demand ramp-up); new timetable periods with new service IDs and schedules |
| Weather and disruptions | Fog (Dec-Feb), monsoon rain (Jul-Aug), heat (May-Jun), road works, protest days |

## 5. Injected dirty data

All 16 SRS defect types are injected by `defects.py` at small, configurable rates
(`defects:` in `generator_config.yaml`). Every defect goes into its **own disjoint set of
rows** chosen with a seeded generator; duplicates copy clean rows only; clean simulated data
never breaks the detection rules. The manifest therefore states exactly what a quality
check should find.

| Defect | Table(s) | How it is injected |
|---|---|---|
| missing ticket records | tickets | ticket rows of APC trips removed (so `card_taps` > ticket rows) |
| missing route IDs | tickets, trips | `route_id` emptied |
| invalid stop IDs | tickets, delays | stop replaced by a non-existent `S9xxx` |
| duplicate tickets | tickets | exact copies of clean rows |
| duplicate trips | trips | exact copies of clean rows |
| negative passenger counts | passenger_counts | boardings, alightings or max_load made negative |
| invalid timestamps | tickets | `entry_time` replaced by unparseable text (e.g. `2025-13-45 25:61:00`, `N/A`) |
| impossible arrival times | delays | actual arrival/departure moved by days or ~100 years |
| departure before arrival | delays | `actual_departure` set 1-10 min before `actual_arrival` |
| vehicle capacity violations | passenger_counts | `max_load` set to 2-3.5x capacity |
| invalid delay values | delays | `delay_minutes` set to text or out-of-range numbers |
| missing vehicle assignments | trips | `vehicle_id` emptied |
| broken stop sequences | route_stops | a middle stop removed (gap) or its sequence number repeated |
| invalid route distances | routes | `distance_km` negative, 0 or 9999 |
| unknown passengers | tickets | `passenger_id` replaced by a non-registered ID |
| missing trip records | trips | trip rows removed while their counts/tickets/delays/GPS remain (orphans) |

`hidden_like` adds new defect types: unknown vehicle IDs, future timestamps, out-of-bounds
stop coordinates and negative fares.

**Manifest.** `data_generator/manifests/<mode>/injection_manifest.json` (outside the
dataset) lists each defect, table, row count and detection rule, plus the orphan rows per
child table; `injection_keys.jsonl.gz` lists the affected keys for precision/recall checks
in Phase 3. `validate_dataset.py` re-detects every defect from the files and requires an
exact match.

## 6. Engineering

### Smart-card coverage limitation

`tickets` represents smart-card journeys only, not all boardings. It is therefore
used for origin-destination analysis and passenger segmentation, while
`passenger_counts` is the source for demand, vehicle occupancy and crowding
metrics. Where a ticket-based result needs an all-boardings estimate, the later
analytics stages must calculate an expansion factor from the observed ratio of
counted boardings to smart-card tickets for the same route and time period; it
must not assume a fixed system-wide percentage.

* **Config-driven:** `data_generator/generator_config.yaml` (`common` + per-mode overrides).
* **Deterministic:** every random number comes from `make_rng(seed, stream, ...)`
  (NumPy `SeedSequence`), with a separate stream per purpose and per month; no clocks or
  unordered sets influence the output. Same config + seed -> byte-identical files
  (checked with SHA-256 checksums, see `data_generator/manifests/<mode>/file_checksums.json`).
* **Chunked:** only one month of events is in memory at a time; reference tables are small.
* **Progress logging:** one line per month; full runs are logged to `reports/processing_logs/`.
* **Output location:** files are written directly to `raw_data/<mode>/` on D:
  (`/mnt/d`). A write test gave 88 MB/s to `/mnt/d` vs 385 MB/s inside WSL; with ~1.5 GB
  of output the difference is seconds, while the run is CPU-bound, so generating in WSL and
  copying was not worth the extra step (decision logged in COMMAND_LOG CMD-006).

## 7. Modes

| Mode | Purpose | Seed | Period | Notes |
|---|---|---|---|---|
| `full` | main dataset | 42 | 2025-09-01 .. 2026-08-31 | 118 routes, 58,000 passengers, 7-day GPS window |
| `sample` | small dataset committed to `sample_data/` | 42 | 2025-10-06 .. 2025-10-12 | 8-route city, higher defect rates so every type appears |
| `hidden_like` | hidden-data readiness | 7 | 2026-09-01 .. 2026-10-31 | same base city as `full` + 5 new routes, new autumn-2026 timetables, 4,000 new card holders, unregistered vehicles, delay-spike days, extra defect types |

Commands (inside WSL, repo root, venv active):

```bash
python -m data_generator.generate --mode full
python -m data_generator.generate --mode sample --publish-sample
python -m data_generator.generate --mode hidden_like
python -m data_generator.validate_dataset --mode full
python -m data_generator.dataset_stats --mode full
```

## 8. Stated limitation: tickets cover smart-card journeys only (accepted, CMD-010)

`tickets` records only journeys made with a **registered smart card** - about 3-4% of all
boardings in the `full` dataset (the monthly card share is in
[dataset_statistics.md](dataset_statistics.md), section 2). Cash riders are counted by the
automatic passenger counters but leave no ticket row. Consequences for all later phases:

| Question | Source table | Why |
|---|---|---|
| Demand, ridership, occupancy, crowding, demand forecasting | `passenger_counts` (APC) | counts **every** boarding on APC-equipped vehicles |
| Origin-destination flows, trip lengths, fares, passenger segmentation (type, age, pass) | `tickets` (+ `passengers`) | only tickets know where a rider tapped in and out and who they are |
| Scaling ticket-based results to all riders | `tickets` x **expansion factor** | factor = counted boardings / card tickets, derived from the data per route and period (Phase 4 feature `ticket_expansion_factor`) |

Tickets must never be used as a direct measure of total demand.
